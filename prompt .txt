# MRITTIKA AI — COMPLETE FULL-STACK APPLICATION BUILD PROMPT

## 0. WHY THIS PROJECT AND WHY THIS FILE STRUCTURE EXISTS

You are building **Mrittika AI**, an intelligent land-record digitization, verification, spatial intelligence, and citizen-access platform designed for a hackathon prototype.

This is **not merely an OCR application**.

The system must demonstrate a complete land-record lifecycle:

```text
Legacy Land Document
        ↓
Upload
        ↓
Image Quality Assessment
        ↓
Image Enhancement
        ↓
OCR / Handwriting Recognition
        ↓
Document Layout Understanding
        ↓
Structured Field Extraction
        ↓
Normalization
        ↓
Confidence Scoring
        ↓
Validation / Anomaly Detection
        ↓
Human Verification
        ↓
Tehsildar Approval
        ↓
Approved Digital Land Record
        ↓
Parcel / GIS Linking
        ↓
Citizen Access
        ↓
Search + Map + Ownership History
        ↓
Grounded AI / RAG
        ↓
Audit Trail
```

The repository must therefore separate:

1. user-facing applications,
2. backend APIs,
3. asynchronous AI processing,
4. database/domain logic,
5. GIS functionality,
6. synthetic dataset generation,
7. model configuration,
8. shared frontend types/components,
9. testing,
10. deployment infrastructure.

Do not put the entire application into a few giant files.

Every major directory must have a clear responsibility.

# 1. PROJECT OBJECTIVE

Build a working prototype called:

# Mrittika AI

Subtitle:

> Intelligent Digitization for India's Land Records

The platform transforms degraded, multilingual and historical land documents such as:

- Khasra
- Khatauni
- Jamabandi
- Record of Rights
- Mutation Registers
- Sale/transfer supporting records
- survey records
- state-specific land forms

into structured, searchable, verifiable and spatially linked digital records.

The hackathon prototype must support four primary roles:

```text
1. Citizen
2. Data Entry Operator — DEO
3. Verifier / Lekhpal
4. Tehsildar
```

These users must NOT see the same dashboard.

Each role receives a separate experience with strict backend authorization.


Initial UI thresholds:

```text

GREEN

0.60 – 0.849
MEDIUM
AMBER

< 0.60
LOW
RED
```

# 78. WHY EACH IMPORTANT FILE/DIRECTORY EXISTS

Do not create files without understanding their responsibility.

## `apps/web`

Contains the browser-based application.

It exists because officer workflows such as document verification, analytics and approval need a large-screen interface.

---

## `apps/mobile`

Contains the React Native/Expo application.

It exists for field capture and citizen mobile access.

Do not duplicate backend business logic here.

---

## `apps/api`

Contains FastAPI.

It is the authoritative application/business layer.

Both web and mobile call this API.

---

## `services/ai-worker`

Contains computationally expensive AI processing.

It is separated from FastAPI because OCR/layout/ML processing should run asynchronously and must not block API workers.

---

## `services/dataset-generator`

Creates synthetic structured land records and corresponding document images/annotations.

It exists because the prototype must be reproducible without relying on private real citizen records.

---

## `services/gis`

Handles synthetic cadastral generation and spatial linking.

It exists because land records must connect textual information to parcels.

---

## `packages/shared-types`

Contains shared TypeScript/domain definitions where appropriate.

It reduces inconsistent frontend schemas.

---

## `packages/ui`

Contains reusable interface components.

Examples:

```text
ConfidenceBadge
RecordStatus
ParcelCard
DocumentStatus
RoleBadge
```

---

## `datasets`

Contains generated training/evaluation/demo data.

Do not mix generated data with application source code.

---

## `models`

Contains model configuration/version registry and local development checkpoints where appropriate.

Do not commit enormous model weights to Git.

---

## `scripts`

Contains reproducible administrative commands.

Examples:

```text
seed demo database
generate dataset
generate GIS
run dataset QA
```

---

## `infrastructure`

Contains deployment-specific configuration.

Application source code should not be mixed with Nginx/Docker/monitoring configuration.

---

## `tests`

Contains cross-service tests and E2E validation.

Tests must verify the entire land-record lifecycle.

---

## `docs`

Contains architecture and implementation documentation so another engineer or judge can understand the system.
