# The interface language

The application speaks English or Hindi. A citizen lands in Hindi, an officer
lands in English, and either can switch.

## Two different languages, deliberately kept apart

This is the distinction that matters, and conflating the two would be a data
integrity bug rather than a presentation one.

| | what it governs | where |
|---|---|---|
| **`UiLanguage`** | the words the *application* says — navigation, buttons, headings, empty states | `packages/ui/src/i18n.tsx` |
| **`DisplayLanguage`** | how a *record value* is shown — as written, or transliterated with the Hindi beside it | `packages/ui/src/record-text.tsx` |

They must be able to disagree. A citizen reading a Hindi interface often wants
owner names transliterated so they can check a spelling; a verifier working in
English must still see the Devanagari exactly as scanned. So the header carries
two switches, labelled differently: **भाषा / Language** for the interface, and
**Show record values in** for the record.

**No record value is ever looked up in a message catalogue.** A village name, an
owner, a khasra number and an area are data. They render through `RecordText`,
which shows the original and can show a transliteration beside it, and they are
never translated (§44). `tests/e2e/bilingual-ui.spec.ts` asserts this directly:
it switches the interface both ways on the same table and compares the numbers
in the cells, which must be identical.

## Defaults per role

| role | default |
|---|---|
| Citizen | **Hindi** — the portal is public-facing and the records are in Hindi |
| DEO, Verifier, Tehsildar | **English** — the revenue service's working language, and what every internal screen, export and audit entry already uses |

A stored choice always wins. The default is a starting point, not a statement
about what anyone can read — the toggle works on every screen for every role,
and an officer reading Hindi is covered by a test.

## Key parity is a type error

`en.ts` is the source of truth for the key set. `hi.ts` declares itself
`Record<MessageKey, string>`, so:

* a key in `en.ts` and not in `hi.ts` fails `tsc --noEmit`
* a key in `hi.ts` and not in `en.ts` fails as an excess property

`npm run typecheck` already runs in CI, so parity cannot drift and there is no
separate lint rule to remember. Both directions were verified by deliberately
breaking them.

`scripts/check_i18n.py` then checks what the type system cannot see — an empty
translation, a Hindi value byte-identical to the English one (the signature of
a key copied across and never translated), and duplicate keys. It runs in CI
right after the typecheck.

## One shared catalogue, two platforms

`apps/mobile` imports the **same** `en.ts` and `hi.ts` through a
`@mrittika/messages/*` path, not a copy. Two copies of a translation drift, and
the drift is invisible until somebody reads the wrong one.

That required teaching Metro about the monorepo (`watchFolders`,
`nodeModulesPaths`, `disableHierarchicalLookup`) — the default Expo config
watches only `apps/mobile`, so a cross-package import typechecks and then fails
at bundle time, a break `tsc` cannot see. Verified by bundling: the exported
mobile bundle contains 430 escaped Devanagari runs.

The *providers* are separate, because the web one renders DOM elements and
reads `localStorage` synchronously while React Native storage is async.

## The switcher is labelled in the target language

Each option's visible text **and its accessible name** come from the language
it switches *to*, never the current one.

This started as a test failure and turned out to be a real accessibility bug:
with the interface in Hindi, the "switch to English" button was announced as
*"इंटरफ़ेस अंग्रेज़ी में बदलें"*. A screen-reader user who cannot read Hindi
could not find the control that exists precisely for them. A switcher is only
useful if every option is legible to the person who wants that option.

## What is NOT translated

Named here so nothing above reads as a claim.

| | status |
|---|---|
| Chrome: navigation, headers, sign-out, language switch, role names | **translated** |
| All six citizen screens (dashboard, my land, search, map, grievances, assistant) | **translated** |
| Mobile citizen route titles | **translated** |
| Officer screen **body copy** — verifier workspace, queue filters, tehsildar approvals and analytics | **not translated** — English only |
| Mobile screen bodies (field capture, citizen screens) | **not translated** — route titles only |
| Login screen body copy | **not translated** |
| Server-side strings — API errors, validation findings, notification templates | **not translated**; notification templates are English, and §34's wording rules are enforced on the English text |
| Number, date and area formatting | not localised — Devanagari digits are preserved in record values but the interface uses Latin digits throughout |
| Right-to-left layouts | not applicable to these two languages, and not implemented |

Officer chrome and navigation *do* switch, and an officer can read the
interface in Hindi — the untranslated part is the body copy of their screens.
That is a deliberate scope boundary given English is their default, not a
technical limitation: the mechanism is in place and extending it is adding keys
and calling `t()`.
