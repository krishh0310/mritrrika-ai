§01

Executive summary

Mrittika AI turns a scanned Khasra page into an approved, spatially linked digital record of rights — and refuses to claim it did so when it did not.

A scanned page enters at one end and leaves as an approved record carrying the same document_id and parcel_id the whole way: quality gate, OpenCV preprocessing, PaddleOCR, region detection, field extraction, normalization, confidence fusion, validation, cross-reference against the cadastre, anomaly detection, human verification, officer approval, and finally a citizen-visible record with a map, an ownership history, a grounded AI answer and a verifiable audit trail.

The figure that matters most in this document is not the highest one. It is 0.59, and the reason it is not higher is stated in §31 rather than obscured: OCR never reaches 26.7% of ground-truth fields, so no extraction method can exceed roughly 73% recall on this corpus. Two of the models built for this system were measured and found not to help. Both are documented at length, because a system that reports only its successes cannot be trusted about any of them.

How to read this document

Every substantive claim carries one of three stamps. Measured means a script in the repository produced the number and it can be reproduced. Partial means it works within stated limits. Not built means exactly that. Section references in the form §22 match the convention used throughout the codebase’s own comments.

§02

The problem

India’s land records are presumptive, not conclusive. A record of rights establishes who the revenue department believes holds a plot — not who legally owns it. Most of that belief is recorded on paper: bound registers of खसरा (plot-wise crop and tenure), खतौनी (holding-wise abstract), and जमाबंदी (record of rights), many of them handwritten, decades old, and degraded.

Digitization under DILRMP has moved millions of these pages into databases. The residual problem is the hard part:

  • The script is Devanagari, and the digits are too. A khasra number reads १४२/२, an area ०.८९. Generic OCR trained on Latin text does not read these, and models that claim multilingual coverage often tokenize Devanagari into meaningless fragments — a point this project measured directly (§12).
  • Pages are damaged in specific ways. Foxing, fold lines, ink fade, stamp bleed-through, skew from a flatbed scanner, and the fibrous texture of decades-old register paper.
  • The units are regional. A बीघा in Uttar Pradesh is 2,529.285 m². In another state it is a different number. An area comparison that assumes one value is silently wrong everywhere else.
  • Errors are consequential. A misread area or a transposed khasra number does not produce a bad search result; it produces a boundary dispute.

That last point sets the design constraint the whole system is built around: the cost of a confident wrong answer far exceeds the cost of saying “a human should look at this”. Every decision documented below follows from it.

§03

Scope and non-scope

What this is

A working prototype covering the full lifecycle of a land record, from a scanned page to an approved, queryable, spatially linked record, with four separated roles and a tamper-evident audit trail. It runs end-to-end on synthetic data and has been driven in a browser across every role.

What this is not

Boundaries stated up front, so nothing below reads as a claim.
BoundaryStatus
Connected to any government systemNot built No DILRMP, BhuNaksha or state RoR integration exists.
Holding real recordsNot built Every parcel, owner, document and mutation is synthetic. Every screen and every exported feature carries a synthetic-data notice.
Security audited / STQC evaluatedNot built Neither has happened.
Accuracy transferable to real registersNot built All figures are measured on generated pages. Nothing about them transfers to a scanned 1950s register.
Multi-state readyPartial SQM_PER_BIGHA is hard-coded to the UP pucca bigha; templates follow three synthetic UP layouts.
The synthetic-data decision

Using generated data was not a shortcut — it was the only way to get ground truth. Because the generator writes the annotation before it renders the page, every field’s true value and pixel position are known exactly. That is what makes an honest accuracy measurement possible at all. It is also why no real citizen’s land is anywhere near this system.

One architectural constraint worth knowing

The worker runs natively during development rather than in Docker. PaddlePaddle publishes no reliable linux/arm64 wheel, and x86 emulation makes OCR far too slow to demonstrate. In production the worker runs on x86_64 Linux, where it does build. This is recorded because planning an arm64 production fleet without re-testing the OCR stack would fail late and expensively.

Degradation is modelled, not simulated with noise

Each page passes through an ordered chain whose parameters are recorded in the annotation: yellowing, ink fade, stains, fold lines, edge damage, perspective warp, rotation, rescale, uneven illumination, brightness/contrast drift, motion and Gaussian blur, Gaussian and salt-pepper noise, and JPEG compression down to quality 32 at the extreme tier.

A defect this work found and fixed

Every tier applies rotation, perspective warp and rescale. The structural region annotations were being written in pre-degradation canvas coordinates while the annotation recorded the post-degradation image size — so the layout ground truth was geometrically wrong on all 500 pages. Nothing read those boxes, so nothing caught it. Layout boxes now travel through the same degrade() call as the field boxes, and a test asserts that annotated table cells fall inside their table region.

Splits are grouped, not random

Documents about the same parcel share a family. A random split would put one page of a parcel in train and another in validation, and the resulting score would measure memorization of that parcel rather than generalization. Splits are grouped by parcel_family so a parcel appears on exactly one side of the boundary.

§06

Pipeline overview

01Quality gate — measured before any model runs; a bad scan is rejected, not processed
02Preprocessing — OpenCV denoise, CLAHE, deskew, upscale; strength chosen by the gate
03OCR — PaddleOCR PP-OCRv5, Devanagari recogniser, reading order resolved
04Layout — table rows from OCR geometry; optional YOLOv8 region detector
05Extraction — label-anchored deterministic rules with per-value strategy provenance
06Normalization — Devanagari digits, units, dates; raw value never destroyed
07Confidence — weighted fusion of five signals, with a breakdown per field
08Validation — deterministic rules over the extracted values
09Cross-reference — the page against the location hierarchy, cadastre and PostGIS geometry
10Anomaly — history rules, then an Isolation Forest for what no rule covers

The ordering is deliberate and is the system’s central design claim: cheap, explainable and deterministic first; statistical only where the deterministic path demonstrably fails. A rule can tell an officer why. A model, in this domain, mostly cannot.

§07

The quality gate comes first

Before any model runs, the page is scored for sharpness, contrast, illumination uniformity, skew, and estimated text density. The verdict is one of PROCESS, PROCESS_WITH_WARNING, RESCAN_RECOMMENDED or REJECT_QUALITY.

A page that fails moves to RESCAN_REQUIRED — never to NEEDS_VERIFICATION with empty results. The distinction matters operationally: a reviewer staring at a blank field list cannot tell whether the record is empty or the scan was unusable. One of those needs a better scan; the other needs a human decision.

The original page is stored regardless of verdict, because an operator told their scan was rejected needs to see the evidence.

§08

Preprocessing is a remedy, not a default

Enhancement strength is chosen from the quality report rather than applied uniformly. A page rated PROCESS is left alone apart from deskewing.

Measured, and counter-intuitive Measured

Running the full enhancement chain over already-clean pages lowered extraction F1 from 0.75 to 0.67. CLAHE and upscaling thin strokes that were already crisp. This is why enhancement is conditional: the obvious “always clean the image” approach actively destroys accuracy on good scans.

Order within the chain also matters and is documented in the code: denoise before any contrast operation, because running CLAHE first amplifies grain that no later filter recovers from. Sharpening is deliberately excluded from the aggressive path — on noisy pages the unsharp mask amplified speckle into false strokes.

Bounding boxes are stored in original page coordinates

Preprocessing deskews and upscales, so OCR returns boxes in enhanced-image space. These are divided back by the scale factors before storage. Without that, the verifier’s click-to-zoom overlay would sit consistently off its words and the whole verification interaction would be useless.

§09

OCR, and the six scripts it reads

Why PaddleOCR

The OCR decision, and what was rejected.
OptionVerdict
PaddleOCR PP-OCRv5Chosen. Ships a dedicated Devanagari recognition model, runs fully offline, no API key, no per-page cost. Detection and recognition are separable, which matters below.
TesseractRejected. Devanagari support exists but conjunct handling on degraded scans is materially worse.
Cloud OCR APIsRejected as primary. Land records are state revenue data; sending them to a third-party endpoint is a data-residency problem before it is a technical one. Also unusable when the venue’s network fails.
Gemini visionRegistered as a fallback only, and its output is flagged degraded so downstream confidence can weight it accordingly.
A trap the code documents so the next person avoids it

Naming any model in PaddleOCR silently disables its language-based selection — it says so only in a warning — and falls back to a recogniser that cannot read Devanagari. Every field then scores zero. A named detector must always travel with its language’s recogniser, named explicitly. The language code is also hi, not devanagari; the latter is the internal model name and raises on use.

Reading order is resolved here, not by callers

PaddleOCR does not return blocks in reading order, and Devanagari cannot be line-grouped by vertical centre because matras and the anusvara inflate box heights. Two words on the same printed line can have y-centres 6 pixels apart while a word on the next line overlaps both. Line grouping therefore uses overlap of the core band rather than centre proximity.

Six scripts, and five refused by name

A land record is not always Devanagari. The same Khasra is Telugu in Telangana, Tamil in Tamil Nadu, Kannada in Karnataka. A pipeline hard-wired to one recogniser does not degrade gracefully on the others — it returns fluent-looking rubbish at a confidence that is low but not zero, and every downstream stage treats it as a reading.

One entry per script, not per language: PP-OCRv5 maps hi, mr, ne, sa, mai and bho onto a single Devanagari recogniser.

Bengali, Gujarati, Gurmukhi, Odia and Malayalam are identified and refused by name. PP-OCRv5 ships no recogniser for them, so language_for_script raises UnsupportedScript rather than defaulting to Devanagari. Identified-and-refused is a page an operator can be told to key in by hand. Unidentified-and-guessed is a record that looks real and is not.

Routing recognises first and decides after

There is deliberately no script-identification model: the script of an image cannot be read off Unicode blocks, and a classifier would add a second thing that can be wrong. Instead each candidate recogniser runs and the outputs are compared. Confidence alone does not decide it — a Devanagari recogniser handed a Telugu page returns '008 28s' at 0.62, low but high enough to win on a sparse page. The score is therefore mean confidence multiplied by the fraction of recognised characters actually belonging to that recogniser’s script.

§10

Region detection: accurate, and it did not help

A YOLOv8n was fine-tuned on the generator’s own structural ground truth — the layout boxes every annotation already carried — over two classes, header and table, on 350 training pages.

Measured Detector quality on the held-out validation split.
ClassPrecisionRecallmAP50mAP50-95
all0.9991.0000.9950.958
header——0.9950.970
table——0.9950.945

On the 75 validation pages it finds a region on every page and returns exactly the ground-truth instance counts: 75 headers, 100 tables.

It does not improve extraction, and that is reported rather than buried Measured

Scoping extraction with those regions moves overall F1 from 0.592 to 0.593 — one false VILLAGE removed across 75 pages. The control arm was re-measured on the same corpus first and reproduced the baseline exactly, so the comparison is like-for-like.

The cause is not detection failure. Extraction is bottlenecked by OCR recall — 0.49, against precision of 0.75 — so the dominant error is a value the pipeline never read at all, which no amount of knowing where the table sits can fix. Reaching across a region boundary for the wrong value turned out to be rare.

The detector is therefore opt-in and off by default: run() takes layout_detector=None and nothing passes one in production. Roughly 3 ms per page after a 0.8 s load is not worth +0.001 F1. It is kept because it is a measured capability with an honest number attached, and because the scoping rule becomes correct once OCR recall improves enough for mis-anchoring to be the limiting error.

Where this could have produced a convincing lie

The obvious scoping rule — “drop page metadata found inside a table” — was checked against the corpus before being written. KHASRA, AREA and LAND_CLASS each appear 333 times as page metadata and 167 times as a table column. That rule would have discarded a third of their true values while raising precision, and would have presented as a large accuracy gain. Scoping is restricted to the eight fields that never appear in a cell.

§11

Field extraction is deterministic first

Extraction is rules over OCR blocks — label proximity, expected position, script and format. Not a model. Land records are forms: a value is positioned relative to a printed label, and three geometries cover the templates.

# the three anchoring geometries
label: value          same line, value to the right      0.90
label —   value      same line, wider gap               0.80
label                grid cell, value directly BELOW    0.78
value

# label variants per field, because the templates differ on purpose
DISTRICT  → जिला, जनपद
VILLAGE   → ग्राम, मौजा, ग्राम / मौजा
KHASRA    → खसरा सं, खसरा संख्या, खसरा

Every extraction carries the bounding box of the value — never the label — so the verifier can zoom to the right region, plus the confidence of the OCR block it came from and the strategy that found it. That provenance is what makes a rule-based extractor more useful to an officer than a marginally more accurate model that cannot explain itself.

Values that cannot be normalised are dropped

Reporting a field as MISSING is honest and reviewable. Emitting से: as a khasra number is a fabricated value that looks like a real extraction. The extractor takes the first option.

§12

A trained extractor was built, and it does not work

A layout-aware neural extractor was built in full — dataset pipeline, model, inference path, per-field fallback, 28 tests. It does not learn. The rules remain the shipped path. This section exists because omitting it would misrepresent everything else in this document.

LayoutLMv3 is the wrong model for Devanagari, measurably

Measured Tokenizing ग्राम रामपुर खसरा १४२/२ क्षेत्रफल — 33 characters.
ModelTokensOutput
layoutlmv3-base55['Ġà¤', 'Ĺ', 'à¥', 'į', 'à¤', '°', 'à¤¾', …]
muril-base-cased8['ग्राम', 'रामपुर', 'खस', '##रा', '१४२', '/', '२', 'क्षेत्रफल']

LayoutLMv3’s byte-level BPE is trained on English: 1.67 tokens per character, as mojibake fragments carrying no pretrained meaning. MuRIL, trained on Indian languages, needs one token per word. LayoutXLM fixes the tokenizer and reintroduces a detectron2 dependency that does not build on this platform. So the model is MuRIL plus LayoutLM’s actual contribution — learned 2D position embeddings summed into the token embeddings, which is the part that matters for a form.

Two real defects found on the way, both worth keeping

  1. Ground truth was in the wrong coordinate frame. enhance_for_quality deskews — a warpAffine rotation — and 70% of pages are rotated. Mapping annotation boxes into OCR space with scale factors alone put them wherever the page sat before it was straightened. The village रामपुर came out labelled B-DISTRICT. Ground truth now travels through the same rotation.
  2. OCR returns lines, not words. PaddleOCR gives तहसील डेमो तहसील as one block — printed label then value — so block-level labelling tagged the label as the value, making 43.6% of supervised tokens contradictory. Splitting into words with apportioned boxes brought that to 35.7%.

The result

Measured After both fixes, with labels verified token by token.

It cannot memorise eight pages it has seen four hundred times. Four explanations were ruled out by measurement, not by argument:

  • Not the architecture — a plain AutoModelForTokenClassification on the same tensors fails identically (loss 1.621, 0 non-O).
  • Not the device — identical on CPU and MPS.
  • Not the learning rate — 2e-5, 5e-5, 1e-4, 3e-4 and 5e-4 all collapse.
  • Not label alignment — the tokenised tensors carry 16 non-O labels on exactly the 16 words the dataset labels, each on the right first sub-token.

The remaining suspect is supervision density — roughly 16 labelled words per page against 70 unlabelled, with heavy token collision between fields whose values share a prefix. That is recorded as a hypothesis, not a finding.

What was gained anyway

The deskew-frame bug is fixed where it would have corrupted any future training run. cache_ocr.py makes a real-OCR corpus reusable, so the next attempt costs minutes rather than an hour. The recall ceiling is now measured. And AI4Bharat’s normaliser (§13) came out of the same work.

The case that matters is the nukta. क़ can arrive from OCR as a single precomposed codepoint or as क followed by U+093C. The two are visually identical and byte-unequal — so a village name matched its own record or did not, depending on which form the recogniser happened to emit. The library’s normaliser converges both, and strips the zero-width joiners scanned text collects. It is optional: absent, normalization behaves exactly as before, which is NFC only.

§14

Confidence is fused, not averaged

Five signals, renormalised over those actually present.
SignalWeightWhat it captures
OCR0.40Recogniser confidence for the block the value came from
Extraction0.25How well the label matched, fuzzily
Layout0.15Which anchoring strategy found it (right-of-label 0.90 … inline 0.62)
Validation0.15Whether deterministic rules objected to the value
Language0.05Whether the script matches what the field should contain

Averaging would let a high OCR score hide a failed validation rule. Weighted fusion, with the breakdown stored per field, lets the verification screen answer why this field scored 0.62 rather than presenting a bare number. Fields at or above 0.85 are auto-accepted; everything below goes to a human.

Not calibrated Not built

These weights are reasoned, not learned. Expected Calibration Error and reliability diagrams are not measured, so a confidence of 0.80 should not be read as “correct 80% of the time”. It is an ordering signal for triage, and the model registry says so.

§15

Validation before ML

Deterministic rules run before any statistical stage: they are explainable, cheap, and produce findings an officer can act on. A rule never blocks a document by itself — it attaches a finding, which feeds the confidence engine and the verifier’s queue.

  • Required fields present (VILLAGE, KHASRA)
  • Area within plausible bounds — 0.01 to 200 bigha
  • Area change ratio against the previous record above 3×
  • Date chronology — mutation dates that run backwards
  • Format conformance for khasra, khata and share fractions

Wording is a rule too. A finding describes an inconsistency, never an accusation. This is enforced by tests that assert no user-facing string contains “fraud”, “fake”, “forged” or “false”.

§16

Cross-reference: the page against the cadastre

Validation asks whether a value is well-formed. A page can satisfy every format rule and still describe a parcel that does not exist, in a village it does not belong to, claiming several times the land on record. Cross-reference asks the other question, against three sources populated independently of any OCR.

Checks, and what each compares against.
CheckAgainst
Village nameThe location the document is filed under — NFC-folded, punctuation-stripped, matched in either script
District, tehsilThat village’s ancestry in the location hierarchy
Khasra numberParcels actually recorded in that village
Khata numberThe matched parcel
AreaThe cadastre’s recorded area, unit-converted, tolerant to 25%
Cadastre self-consistencyThe recorded area against ST_Area of the polygon it stores

Three judgements worth naming

  • Findings live in their own response key, not merged into format findings. A format rule is about the page alone and a verifier can settle it from the scan. A cross-reference finding is a disagreement in which the page is often the correct side — the cadastre is itself derived data. Merging them would invite editing the document to match the reference.
  • A missing field produces no finding. It is already reported as MISSING; adding “and it does not match the cadastre” is the same fact twice.
  • An unconvertible unit produces no finding rather than a guessed conversion factor.

Verified against real processed documents, not fixtures: it correctly reports a page naming रामपुर filed under Mudiyakala, with a khasra recorded in neither.

Area conversion lives in mrittika_domain.area, now the single source of truth for SQM_PER_BIGHA and friends — the GIS service imports it rather than keeping a second copy that could drift while both halves still looked self-consistent. The geometry check casts to geography, because ST_Area on a raw 4326 geometry returns square degrees.

§17

Anomaly detection is two engines, separated

The division of labour is explicit: rules detect deterministic inconsistencies; ML detects unusual patterns; the LLM explains evidence — elsewhere, never here.

Rules first

Area jumps, invalid chronology, duplicate parcels, missing mutations, location mismatches, repeated modification, unusual ownership change. Each fires on its own condition and carries checkable evidence.

Isolation Forest for what no rule covers

Unsupervised, over 10 parcel features. It learns what the corpus looks like and scores how easily a record separates from it. Three engineering decisions:

  • Minimum corpus of 30. A forest fitted on five parcels would call almost anything an outlier.
  • Contamination 0.05. Deliberately low — a false flag costs an officer’s time and erodes trust in every other flag.
  • Suppressed when a rule already fired. Telling an officer “this is unusual” on top of “these dates run backwards” adds noise, not information.

An outlier score carries no explanation, which is why every flag it produces is worded as “unusual relative to comparable records” and ranked below any rule finding. Without scikit-learn, or below the corpus floor, the rules run alone and nothing is fabricated.

§18

The grounded assistant

Both citizens and officers can ask questions in natural language. The retrieval design has one non-negotiable property: authorization precedes retrieval.

# embeddings table carries scoping columns so filtering happens
# BEFORE similarity search, not after
parcel_id   → FK, indexed
village_id  → FK, indexed
content     → only from APPROVED records

Only content derived from approved records is embedded at all, so the retriever cannot surface an unapproved document even before authorization filtering applies. A citizen’s query is scoped to parcels they hold; an officer’s to their jurisdiction.

Every answer cites the record it came from. When retrieval returns nothing the caller is entitled to see, the assistant says so rather than answering from the model’s parameters — which in this domain would mean inventing a land record.

Embeddings and generation use Gemini; the provider is behind an interface and the model version is recorded on every answer.

Why so few trained models — on purpose

The governing principle is: start with what is explainable and cheap, measure where it fails, and only then reach for a fine-tuned model. Two attempts to reach past that line were made in this work — a region detector (§10) and a token-classification extractor (§12). Both were built completely and measured. Neither improved the system. Both are documented. The rules ship.

Analytics & metrics✓

Two separations are load-bearing. A verifier cannot approve — the person who corrects the AI is not the person who signs off, which is the standard revenue-department control. And citizens never see internal AI signals: confidence scores, anomaly flags and raw OCR are officer-only, because a citizen shown “anomaly score 0.72” on their own land has been told something the system cannot responsibly explain.

§21

Document lifecycle

UPLOADED → QUALITY_CHECK → PROCESSING → AI_EXTRACTED
         → NEEDS_VERIFICATION → UNDER_VERIFICATION → VERIFIED
         → PENDING_APPROVAL → APPROVED

  side exits:  REJECTED · RESCAN_REQUIRED · ARCHIVED

Transitions are validated server-side against an explicit graph. There is exactly one sanctioned way to change a document’s state, and it writes an audit event in the same transaction — a service that assigns the column directly bypasses both the graph and the audit trail, so none does.

UPLOADED → APPROVED is unreachable by construction, and there is a test that proves it.

The audit trail is a hash chain

Each event carries the hash of its predecessor, so any retrospective edit breaks the chain from that point forward and is detectable. It is described as tamper-evident, single-writer — explicitly not a blockchain, because there is no consensus and claiming otherwise would be dishonest about what it guarantees.

§22

Duplicate detection, in two tiers

Two different questions, answered differently — and collapsing them would be the mistake.

QuestionMethodResponse
Are these the same bytes?SHA-256, checked before storage409 Conflict, naming the document that already holds them
Does this look like the same page?64-bit dHash, Hamming distance ≤ 10Accepted and flagged for an officer to judge

A SHA-256 match is not a judgement call: the file is already stored, and re-running OCR would burn a worker slot to produce a second copy of an answer the system already has. A near match is a different matter entirely — a rescan after a quality rejection produces exactly that signal, and refusing it would block the remedy the system just requested.

Why dHash

Chosen over aHash because each bit records whether a pixel is brighter than its right-hand neighbour — a comparison, not a level — so uniform brightness and contrast changes cancel out, which is most of what a second pass through a scanner does. Chosen over pHash because it needs no DCT and therefore no new dependency.

The hash is computed inside the quality gate, where pages are already decoded; a second decode would double the gate’s cost to learn something the first decode already had in hand.

What this exposed elsewhere

Anomaly flags were being reported with a parcel and no document. An upload-time flag names only a document, so an officer received a finding with a null parcel and no way to reach what it was about. The listing now joins Document as well.

§23

Active learning, without autonomous retraining

Every verifier correction now enters a curated retraining pool, scored by how much it would teach. The ranking runs in the direction that is easy to get backwards:

Selection reasons, most informative first.
ReasonPriorityWhy
CONFIDENT_BUT_WRONG0.80–1.00Returned ≥ 0.85 and still corrected. A systematic error the model cannot see.
MISSED_ENTIRELY0.60No prediction at all — a recall problem, already visible as MISSING.
MODERATE_MISS0.45–0.75Middle band.
UNCERTAIN_AND_WRONG0.20–0.40Returned ≤ 0.55 and corrected — the confidence engine working as designed. Far less signal.

Nothing retrains itself. Rows arrive reviewed=False, and readiness is a report a human reads, not a trigger — unreviewed rows never count toward it. Automatic nightly retraining on unreviewed verifier edits would let a single mistaken correction, or one operator having a bad afternoon, teach the model directly.

The pool endpoint returns which corrections are informative and never what the corrected values were; reading record content stays behind the verification screens and their own authorization.

§24

Record certificates a citizen can print

A downloadable record-of-rights extract with a verifying QR code. Three decisions, each ruling out the obvious approach.

Not reportlab

ReportLab does not shape Devanagari — it places glyphs left-to-right without the substitutions Indic scripts require, so conjuncts come apart and matras attach to the wrong consonant. A land record rendered that way does not merely look wrong; it says something different. The page is drawn with Pillow, which this project already requires to be libraqm-linked, and saved as PDF from there.

The QR does not carry the record

A QR containing the contents is a record that can be edited by regenerating a QR. It carries a URL and a SHA-256 over a canonical serialisation, so verifying means asking this system whether such a certificate was issued for that parcel. The paper cannot vouch for itself.

Verification returns match-or-not, and nothing else

If the check replied with the record, a photograph of somebody’s paperwork would become a way to read their holdings. A mismatch is worded as out of date, not forged — a record legitimately changes when a mutation is approved.

An honest cost, pinned by a test Partial

The page is rasterised, so the PDF has no text layer: it cannot be searched, copied from, or read by a screen reader. That is the price of correct Devanagari shaping here. A test fails loudly if a text layer ever appears, so the documentation and the limitation stay in step.

§25

Batch upload, where partial success is normal

A DEO uploads a tray of scans in one request. The endpoint returns 207 Multi-Status, not 201, because partial success is the ordinary outcome rather than an edge case: a day’s scanning routinely contains a page already filed, a page that is not an image, and thirty-seven that are fine.

A batch that failed as a unit would make the operator re-upload everything to fix one file. A batch that succeeded as a unit would swallow the two bad pages. So the response is two lists — what landed, and what did not with the reason — and the screen renders it that way.

No bulk fast-path

Every file goes through the same upload() call as a single upload: same quality gate, same duplicate check, same audit event. A shortcut is exactly where per-document guarantees would quietly stop applying, so there isn’t one, and a test asserts every batched document still carries a quality verdict.

Rejections are counted apart from quality failures — a file that was never stored and a page that was stored and needs rescanning are different problems with different remedies. The screen asks only for what is true of the whole tray; khasra and khata differ per page, so a field for them here would invite one number being applied to forty documents.

§26

Notifications built around approved templates

Two regulatory constraints shaped this more than any design preference.

  • WhatsApp Business Cloud API requires a template approved by Meta for any business-initiated message outside a 24-hour reply window.
  • SMS in India is governed by TRAI’s DLT regime: each transactional template must be registered against a principal entity. A message without a valid DLT template ID is accepted by the gateway and dropped by the operator — a delivery failure that looks exactly like a success.

So the unit of sending is a template plus variables, never a string. Both providers refuse to send on a missing or placeholder template ID rather than report a false success.

A notification is delivered to a phone, and a phone has no authorization

It is read on a lock screen, in a household that may contain the other party to a land dispute. So no template carries record content. None names a person, a khasra number or an area — each says something changed and to sign in. Template variables are restricted to a reference and a status, and a test asserts that on every template, including that extra values passed by a caller cannot be interpolated into a body.

Triggers: a grievance status change notifies the citizen who raised it; an approval notifies citizens who currently hold a share (valid_to IS NULL). Notifying a former owner that a record they no longer hold has changed is a disclosure, not a courtesy.

Nothing in the workflow depends on a gateway. The in-app notification is written first and unconditionally; with no credentials configured the dispatcher records the attempt and everything else behaves identically.

§27

The bilingual interface

Two things both call themselves “language”, and keeping them apart is a data-integrity matter rather than a presentation one.

MechanismGoverns
UiLanguageThe words the application says — navigation, buttons, headings, empty states
DisplayLanguageHow a record value is shown — as written, or transliterated with the Devanagari beside it

They must be able to disagree: a citizen reading a Hindi interface often wants owner names transliterated to check a spelling, and a verifier working in English must still see the Devanagari exactly as scanned. No record value is ever looked up in a message catalogue. A browser test asserts it the only way that means anything — it switches the interface both ways on the same table and compares the numbers in the cells, which stay identical while every column heading changes.

Citizens default to Hindi; officers to English. That is a starting point, not a statement about what anyone can read — the toggle works on every screen for every role, and an officer reading Hindi is covered by a test.

Key parity is a type error

hi.ts declares itself Record<MessageKey, string>, so a missing key fails tsc and an extra one fails as an excess property. That runs in CI already, so parity cannot drift and there is no separate lint rule to remember. A companion script catches what types cannot see — an empty translation, a Hindi value byte-identical to the English one, a duplicate key.

A real accessibility bug found by a failing test

With the interface in Hindi, the “switch to English” control was announced as “इंटरफ़ेस अंग्रेज़ी में बदलें”. A screen-reader user who cannot read Hindi could not find the control that exists precisely for them. Both the visible text and the accessible name now come from the language each option switches to.

Mobile imports the same catalogues rather than a copy — verified by bundling, with 430 escaped Devanagari runs present in the exported bundle. Partial Officer screen body copy is not translated; their chrome and navigation are.

§28

GeoServer — why it exists

The application already serves parcel geometry as GeoJSON. GeoServer adds nothing to the project’s own map. What it adds is protocol.

The need

A state revenue portal, a BhuNaksha-style viewer, a planning department’s desktop GIS, or a tehsildar opening QGIS all speak WMS and WFS — OGC standards. None of them can consume a bespoke JSON endpoint without someone writing an adapter first. For a system whose entire premise is integrating with existing land-record infrastructure, exposing the cadastre over the protocols those systems already speak is the difference between “we have an API” and “you can add this as a layer”.

The honest limit of that argument

GeoServer is needed if integration with government GIS is on the roadmap, and dead weight if it is not. For demonstrating the project’s own UI you would never start it. That is exactly why it is an opt-in compose overlay rather than part of the default stack, and why it binds to 127.0.0.1.

The design problem: GeoServer has no idea who is asking

It cannot evaluate gis:view. It cannot scope to a tehsildar’s jurisdiction. It has no principal at all — it serves whatever its database role can read, to whoever reaches its port. And the OGC protocols make that generous by design: WFS GetFeature with outputFormat=csv hands over the entire attribute table of any visible layer.

So the protection is not in GeoServer’s configuration, which an admin can change in a web UI. It is in two places that cannot be changed by accident.

1 · The view

GeoServer is pointed at gis_published_parcels, never at parcels:

  • Approved records only — a parcel with no approved land record does not appear, the same rule citizen search applies.
  • No ownership — not a redacted column, no owner join at all. There is no query against this view that returns a person’s name.
  • No internal AI signals — no confidence, no anomaly score, no document state. A WFS attribute table is the widest possible “outside”.

A test pins the published column set to an explicit allowlist, so a column reaching the public layer breaks a test before it reaches a consumer.

2 · The database role

geoserver_reader holds SELECT on that one view plus the two PostGIS metadata tables a spatial layer cannot load without. It is not a matter of policy that a WFS request cannot return an owner’s name — the role cannot read the table:

$ psql -U geoserver_reader -c 'SELECT * FROM owners LIMIT 1;'
ERROR:  permission denied for table owners

The provisioning script additionally refuses to build a store on postgres, mrittika, root or admin, because the store’s credentials are the authorization boundary.

What it serves Measured

Verified running, not merely configured: GeoServer 2.28.2 up, role created, layer provisioned, and the seeded 160-parcel cadastre served back as GeoJSON over WFS (polygons, no owner attribute) and as a rendered PNG over WMS showing the Voronoi parcel boundaries. Every feature carries is_synthetic: true and a DEMO / SYNTHETIC DATA notice at the feature level, so a consuming system cannot mistake it for a real cadastre.

§29

Prometheus & Grafana — why they exist

The strongest argument for this one is that the instrumentation was already there and nothing was reading it.

The need

/metrics has emitted Prometheus text format since the project’s first commit — nine metrics covering HTTP counters, a latency histogram, queue depth, failure counts, stage latencies, confidence and correction rates. Someone had already decided this application should be Prometheus-scraped. What was missing was something to scrape it and somewhere to look.

It also answers a different question from the tehsildar’s analytics screen, which already exists. That one asks how is the digitisation programme going. This one asks is the worker consuming the queue right now — which is what you need when a DEO reports that uploads are not processing.

The nine metrics, and the operational question each answers.
MetricAnswers
mrittika_processing_queue_depthIs the worker consuming? A flat non-zero line means it is not.
mrittika_documents_by_stateWhere work is piling up. Growing NEEDS_VERIFICATION with flat APPROVED is a staffing problem, not a pipeline one.
mrittika_ai_failures_totalPipeline defects, as distinct from bad scans.

mrittika_http_request_duration_secondsp50 / p95 latency.

The design problem: Prometheus cannot hold a JWT

/metrics was gated behind analytics:view, but Prometheus has no login and its bearer credentials are static. The endpoint therefore accepts either that permission or a scrape token, compared with hmac.compare_digest so an early-exit comparison cannot leak the token’s length and prefix to anyone timing the response.

With the token unset there is no token path at all. That is the safe default: a misconfigured scraper fails to authenticate rather than silently publishing workload and queue depth. The token is mounted from a gitignored file rather than written into the committed prometheus.yml — a committed credential is a leaked credential.

A test that keeps the dashboard honest

Every metric the dashboard queries is asserted to be one the API actually emits, checked against the live exposition rather than a hard-coded list. Renaming a metric now breaks a test instead of leaving an on-call engineer staring at an empty panel. This was verified by deliberately renaming one and watching the test fail.

Verified running Measured

Grafana’s datasource and dashboard are provisioned from files, not clicked in the UI — one configured by hand lives only in that container’s volume and is lost with it. Both ports bind to localhost: an exposed Prometheus is a description of the system’s behaviour handed to anyone who asks.

Not done

Not built Alerting rules (the dashboard shows, it does not page); worker-side metrics (queue depth is read from the database, not from Celery); log aggregation; tracing; long-term storage beyond 15-day local retention.

The recurring principle is authorization before retrieval. Embeddings carry scoping columns so semantic search filters before similarity, not after. The GIS view is an authorization boundary expressed in SQL. The metrics endpoint has two doors and no third.

§33

What makes it different

1 · It refuses to fabricate

Every provider has an explicit failure contract. A failed OCR provider raises; the caller falls back; if every provider fails the region is marked NEEDS_REVIEW and the document moves to RESCAN_REQUIRED. A value that cannot be normalised is dropped and reported missing rather than emitted as plausible-looking text. An unsupported script is refused by name rather than handed to whichever recogniser happens to be loaded. This is one consistent rule applied about twenty times across the codebase.

2 · Measurement decides, including against itself

Two models were built to completion in this work and both were found not to help. Both are documented with the numbers that killed them. The enhancement chain is conditional because measurement showed it lowered F1 on clean pages. The registry was corrected to remove three models it falsely claimed. A system willing to publish its negative results is one whose positive results mean something.

3 · Authorization precedes retrieval, everywhere

Not a middleware check bolted on top: embeddings carry scoping columns so semantic search filters before similarity; the GIS layer is a SQL view with a role that physically cannot read the owners table; the metrics endpoint has two doors and no third; verification of a printed certificate returns match-or-not and never content.

4 · Provenance on every value

Each extracted field records its raw OCR text, its normalized form, any human correction, its bounding box, five confidence components, the strategy that located it, and the model version that produced it. An officer can ask why does this say 0.62 and get an answer. Very few extraction systems can.

5 · The domain is respected, not approximated

Ownership is time-bounded rows, never an owner column, because that is what makes “who owned this in 1998” answerable. Shares are stored as written fractions (1/2), never floats, because rounding a recorded share changes its legal meaning. The bigha is documented as a UP-specific constant that must become configurable. Findings never accuse anyone, and tests enforce the vocabulary.

6 · It is honest about being a prototype

Every screen, every exported GIS feature, every PDF and every notification carries a synthetic-data notice. The deployment document lists seven things that must happen before this could carry a real record, starting with a security audit. The scope section of this report was written before the features section.

§34

Deployment

Intended target: NIC MeghRaj

The choice is regulatory rather than technical. Records of rights are state revenue data, so residency on government-controlled infrastructure inside India is expected; state revenue departments procure through NIC or MeitY-empanelled providers, so a deployment outside that list is not procurable however well it runs; and DILRMP, BhuNaksha and existing state RoR systems are already inside that network, where an integration is a smaller security surface than one crossing the public internet. A suite that could only pass once

The browser tests uploaded corpus files verbatim. Once duplicate detection landed, the first run stored those files and every run after was rejected as a duplicate — so the suite passed exactly once and then failed forever, in a way that looked like a regression in the feature rather than in the fixture. A shared helper now appends bytes after the JPEG end-of-image marker, changing the hash without changing what any reader sees. Verified by running the full suite twice in a row.

§36

Where the effort should go next

The measurements in this report point in one direction, and it is not the direction most roadmaps take.

  1. OCR recall, not extraction. 26.7% of fields are never read. Two extraction models were built and neither helped, because the bottleneck is upstream of them. Fine-tuning the Devanagari recogniser on degraded register pages is the single highest-value piece of work available.
  2. Handwriting. Nothing currently detects it, let alone reads it. Older registers are substantially handwritten, so this is a correctness gap before it is a feature gap.
  3. Confidence calibration. The banding decides what a human sees. Until ECE is measured, that threshold is a reasoned guess.
  4. Per-state configuration. The bigha constant and the template vocabulary both need to become configuration before a second state is possible.
  5. Then, and only then, the extraction model. Once OCR recall rises, mis-anchoring becomes the limiting error — and the region detector and scoping rule already built become worth switching on.

Every figure in this document was produced by a script in the repository and can be reproduced. Where a number is absent, it is because the measurement has not been made — and that is said rather than filled in.
